# ADR-001: Component Filter for Stage 1 Centerline Extraction

**Status:** Accepted
**Date:** 2026-05-19
**Scope:** Stage 1 of the staff detection pipeline — line-pixel isolation within a detected staffline bounding box, prior to curve fitting.
**Supersedes:** N/A
**Related:** [[Staff Detection Pipeline — Design Decision Document]] (§5)

---

## Context

Stage 1 of the staff detection pipeline must take a detected staffline bounding box and isolate the line's pixels from other contents of the box (neumes sitting on the line, text crossing it, fragments of neighbor lines intruding into tall/skewed boxes, background noise) so that a curve can be fit to the resulting pixels and a precise centerline produced.

The initial design assumed classical-CV component filtering with binarization, connected-components analysis, and a multi-factor scoring function. Two refinements emerged during design:

1. An existing background-removal (BGR) script — trained on manuscripts and fragments — is available and outputs RGB-on-white images. Integrating it upstream of stage 1 substantially cleans the input.
2. The fit (stage 1's downstream step) will use robust regression (RANSAC or Huber), which tolerates local asymmetry from non-line pixels mixed into a line-bearing component. This means the component filter does not need to precisely excise non-line ink; it needs only to keep the right component.

Together, these refinements simplify the component filter's responsibilities and reshape several of its design choices.

## Decisions

### 1. Preprocessing

BGR runs at the page level, upstream of stage 1, exactly once per page. Stage 1 operates on background-removed crops. BGR output is RGB on a white background; stage 1 converts to grayscale and applies Otsu thresholding to obtain a binary image for connected-components analysis.

### 2. Filter permissiveness

The component filter's goal is to **keep the component that contains the line**, not to extract only the line pixels. Lumpy components (a staffline with neume blobs attached) are acceptable inputs to the fit. Robust fitting downstream handles local pixel asymmetry; the filter does not need to.

### 3. Aspect ratio as floor, not score

Aspect ratio is used only as a **filtering floor**: a component must be at least wider than tall to be considered at all. It is not a sub-score in the ranking among surviving candidates. This avoids penalizing exactly the shapes the permissive-filter decision commits to keeping (lines with neumes on them).

### 4. Scoring function

Among components passing the aspect-ratio floor, ranking is by a weighted sum of two normalized sub-scores:

- **Horizontal extent:** longer is better (a staffline spans most of its bounding box).
- **Proximity to box vertical center:** closer is better (the target line should sit near the middle of its own bounding box; intruding neighbor fragments typically appear near top or bottom edges).

Weights are named constants at the top of the function. Initial values: 0.5 each. Revisit if experiment data suggests asymmetric weighting.

### 5. Ambiguous boxes (multiple viable components)

When more than one component survives filtering and scores comparably, emit one record for the highest-scoring component and set `quality.flags` to include `multiple_components_kept`. The discarded candidates and their scores are recorded in the output for inspection.

### 6. Function interface

The component filter function takes a **cropped, BGR-preprocessed NumPy array** representing one detected bounding box. Callers are responsible for loading the page, running BGR, and cropping the box. This keeps the filter focused on its one job; a thin wrapper can orchestrate the page-level steps for the existing BGR script's interface.

### 7. Function output

The function returns a `dataclass` with the following fields:

- `coords`: list of `(x, y)` tuples of kept pixels — direct input to the fit step.
- `mask`: boolean NumPy array the same size as the input crop — for diagnostic visualization.
- `score_breakdown`: per-component scoring details — for logging and tuning.
- `discarded`: list of discarded candidates with their scores — supports the `multiple_components_kept` flag logic.
- `flags`: list of strings indicating notable conditions (e.g., `multiple_components_kept`, `no_components_survived`). Mirrors the `quality.flags` convention in the Stage 1 output schema.

### 8. Library choices

Python with OpenCV (`cv2`), NumPy, and Matplotlib (for diagnostic visualizations). Matches the existing OMR pipeline's toolset (`cv2` and PyTorch already in use).

### 9. Implementation parameters (initial values)

The following are tunable constants at the top of the function. All values are starting points to be revisited based on experiment results.

- **Aspect-ratio floor:** `width / height > 2.0`. Components failing this are discarded as not-a-line-candidate. Lines on real manuscripts are typically much wider than tall; 2.0 is a generous floor that excludes square/compact glyphs while accepting lines with neume blobs.
- **Minimum component size:** `5 * h` pixels, where `h` is the scale unit (page-level median staffline thickness). Components below this floor are discarded as noise (dust, JPEG artifacts, isolated specks surviving BGR). At `h=2` this is 10 pixels; at `h=24` it is 120 pixels — both reasonable noise floors.
- **Connectivity for connected components:** 8-connectivity (diagonal neighbors count as connected). Avoids breaking slightly-stepped lines into fragments.
- **"Comparable score" threshold for `multiple_components_kept` flag:** Second-place score within 20% of first-place. Flags ambiguity for QA inspection without triggering on clear winners.

### 10. Scale unit handling

The scale unit `h` (page-level median staffline thickness in pixels) is passed in as a function argument with a sensible default. This keeps the function honest about its dependency on scale and lets the caller decide whether to compute `h` page-wide, per-box, or use a fallback. Per-box derivation may be added later if local scale variation within a page proves problematic.

### 11. Diagnostic visualization

When a `save_path` is provided, the function renders a multi-panel Matplotlib figure showing:

- The original BGR-preprocessed crop.
- The binarized (Otsu) image.
- All connected components labeled with distinct colors, with kept and discarded candidates visually distinguishable.
- The final kept-component mask alone.

Each panel is labeled. The figure is saved as PNG. If no `save_path` is provided, visualization is skipped (no rendering overhead during batch runs).

### 12. Empty-result handling

When no components survive filtering (e.g., a faded line, a detector hallucination, or a box where BGR removed all ink), the function returns a normal result with empty `coords` and `mask`, and a `no_components_survived` entry in `flags`. The caller decides what to do; the function does not raise.

## Rationale Summary

The combination of BGR preprocessing (removes background as a failure mode), permissive component filtering (keeps lumpy line-bearing components), and downstream robust fitting (suppresses local asymmetry) covers the majority of realistic box contents without requiring elaborate per-step parameter tuning or a learned line-isolation model. The filter becomes a simple, inspectable, classical-CV step whose only job is to find the right connected component.

## Consequences

**Simplifications:**

- Binarization is a one-liner (Otsu on grayscale of BGR output); no need for adaptive thresholding or document-specific binarization methods.
- The component filter has few tunable parameters: aspect-ratio floor, minimum-component-size multiplier, two scoring weights, and the comparable-score threshold.
- The filter does not need to precisely segment the line from non-line ink within a kept component.

**Costs and accepted risks:**

- The filter relies on BGR running correctly upstream. BGR failures (uncleaned background, false ink suppression) propagate into the filter as garbage-in. Detectable in diagnostic visualizations during the experiment.
- The filter does not handle ink-on-ink ambiguity where the line is genuinely fused topologically with a neighboring line (e.g., through a ligature stem). These cases remain hard for any approach and are partly detector-quality concerns. They will be flagged in logs rather than designed around in the proof of concept.
- The minimum-component-size filter depends on `h` being available. If the caller does not provide `h`, the default fallback may be too lax or too strict for some manuscripts; this is a known limitation accepted for the proof of concept.

## Escalation Paths

If experimental results show failure concentrated in specific categories, the following escalations are pre-considered:

- **Failures clustered in the populated category** (neumes on line) despite BGR + permissive filter + robust fit: introduce a learned line-isolation model narrowly targeted at ink-on-ink ambiguity. Inputs and outputs of the model would match the current filter's interface, making it a drop-in replacement.
- **Failures from topological line fusion**: escalate to the upstream detector's box-tightness; a tighter box that doesn't include the neighbor sidesteps the fusion.
- **Failures from BGR misbehavior on a manuscript class**: revisit binarization (escalate from Otsu to Sauvola or similar), or retrain BGR on the failing manuscript class.

## Deferred Decisions

The following are explicitly out of scope for this ADR and will be settled in subsequent work:

- Fit method specifics (RANSAC vs. Huber vs. plain least squares; robust fitting is committed to, the choice between robust methods is not).
- Sampling the fitted curve to integer x.
- Full Stage 1 output schema record assembly.
- Per-box local scale unit derivation (if page-level scale proves insufficient).
- Orchestration across many boxes within a page.

## Notes

- Initial scoring weights (0.5 each) and other tunable constants are starting points. The experiment plan in the design document includes parameter-tuning as one of its outputs.
- The `multiple_components_kept` and `no_components_survived` flags are the primary signals that human QA or upstream-detector inspection may want to revisit a given line. The discarded-candidates record exists to support that inspection.
- The function signature and dataclass fields are stable interface commitments; internal scoring details and filter thresholds are tunable.
